## 1. Technique Comparison

| Technique | What it does to the data | Can the original be recovered, and by whom? | Concrete healthcare use case | Important limitation |
|---|---|---|---|---|
| **Encryption** | Transforms readable plaintext into ciphertext using a cryptographic algorithm and key; authenticated encryption also detects unauthorized modifications. | **Yes**, by a party holding the necessary decryption key and authorization; key loss may make legitimate recovery impossible. | Encrypt MedDefense EHR database volumes, PACS storage, and authenticated clinical network traffic using appropriate modes/protocols. | Does not remove access needs: data is plaintext after authorized decryption, and stolen keys defeat confidentiality. |
| **Hashing** | Computes a fixed-length digest from input; conventional cryptographic hashing is one-way and useful for integrity checks. | **No decryption operation**; an attacker may *guess* low-entropy inputs and compare digests (especially passwords). | SHA-256 file-integrity verification of a clinical document or signed software update; use a password KDF rather than raw SHA-256 for passwords. | A bare hash is not proof of authenticity: an attacker able to replace both the file and its reference hash can fool the check. |
| **Tokenization** | Substitutes a sensitive value with an opaque surrogate token and, in a vault-based model, records a protected mapping. | **Yes**, only through an authorized tokenization provider/vault mapping or controlled de-tokenization service; a well-designed opaque token alone reveals no PAN. | Store payment-provider tokens in `billing-srv-01` instead of full credit-card primary account numbers (PANs). | A token may still authorize transactions through an API; vault and payment privileges remain high-value targets. |
| **Data masking** | Conceals or substitutes selected fields in a user view, response or derived dataset according to context and role. | **Sometimes**: the original is typically retained in the source system and accessible to approved roles, but irreversible redaction in an exported copy cannot be undone from that copy. | Show billing staff only an authorized minimum subset of patient identity and diagnosis; hide clinical diagnoses from reception. | Merely masking a web page while the API returns the unmasked value is not a security boundary. |
| **Steganography** | Conceals a payload within an otherwise plausible carrier such as an image, audio object or file structure; it hides the *presence* of data rather than necessarily encrypting it. | **Potentially**, by someone who knows the extraction method and any required key; observers may not notice an embedded payload. | Legitimate, separately approved image watermarking/provenance research; assess hidden-data exfiltration in DICOM image workflows as a threat. | Does not inherently provide confidentiality, integrity or tamper evidence, and can threaten diagnostic image fidelity. |

**Security+ distinction:** Encryption provides confidentiality through keys; hashing provides a one-way digest; tokenization substitutes identifiers backed by a secure mapping; masking restricts exposure in a view; steganography disguises the existence of content. The techniques are complementary, not interchangeable. A digital signature or authenticated MAC is needed when *authenticity* must accompany an integrity check.

## 2. MedDefense Payment Tokenization Design

### 2.1 Goal, data, and token format

MedDefense Billing must collect authorized patient payments without retaining full payment card numbers on its MySQL server or other MedDefense-controlled application hosts. **Tokenize the card's PAN** (and keep cardholder or billing-address data only when justified); do **not** persist CVV/CVC, magnetic-stripe data or PINs after authorization. Prefer a **PCI DSS-validated payment processor/tokenization provider** using a hosted payment field or redirect so the PAN goes directly from the patient to the provider, not through MedDefense's application server.

**Proposed opaque token example:** `md_tok_v1_8f2c7a60d91e4b3f9a056c18e722d4ab`.

- `md_tok_v1_` is a human-readable namespace/version label; the remaining **32 hexadecimal characters represent 128 uniformly random bits** generated by a cryptographically secure random number generator. This is an illustrative format, **not a real payment-provider token**.
- Tokens must be unique, non-sequential, non-PAN-derived, merchant/tenant-scoped and restricted to an authorized payment use; use the actual processor format if it differs.
- A payment-method token may be reusable for approved refunds/recurring payments; a separate short-lived, single-use authorization token is safer where repeat use is unnecessary.
- Keep a separate **internal billing record ID**, processor token, brand and at most masked last four digits/expiry where operationally justified. Never insert full PAN or secret API credentials into SQL query logs, error traces, analytics, tickets or backups.

### 2.2 Architecture and location of the vault

**Preferred location:** A provider-controlled token vault in the isolated PCI cardholder-data environment (CDE), **outside** MedDefense's PostgreSQL, MySQL and NAS infrastructure. The MedDefense billing database keeps only the opaque provider token and approved non-sensitive receipt metadata; it has **no direct de-tokenization API permission**. A processor's restricted payment API uses the token to initiate a charge/refund without returning the PAN to MedDefense.

```text
Patient -> Hosted payment form -> PCI payment provider -> encrypted PAN vault
                                  |                 ^
                                  v                 | limited provider-only detokenization
                         Scoped opaque token -> MedDefense billing MySQL
                         MedDefense -> provider charge/refund API (authorized token)
```

**If a MedDefense-operated vault is unavoidable (fallback, not preferred):** place it in a dedicated, firewalled CDE separate from `billing-srv-01`; encrypt PAN and encrypted backups using vetted AES-256 authenticated encryption (or an approved storage-layer design), keep encryption keys separately in a managed KMS/HSM, and restrict decrypt/detokenize operations to narrowly authenticated service identities. Apply TLS 1.2/1.3, mutual authentication where appropriate, MFA for privileged access, least-privilege RBAC, dual control for key recovery, key rotation, patching, hardened hosts, tamper-evident audit logs, alerting, rate limits, tested recovery and independent assessment. No database account, billing clerk or front-end component receives raw PAN by default.

**Payment flow / required control points:**

1. Patient enters card details into the provider's hosted field over authenticated HTTPS; MedDefense must not collect or log the PAN.
2. The provider validates and stores the PAN in its protected environment and returns a limited-purpose opaque token (or reports a failure without a token).
3. MedDefense binds the token to the correct patient/billing account after validating the provider response, customer authorization and transaction context; prevent account-mapping and replay attacks.
4. An authorized billing backend requests a permitted charge/refund through a server-to-server processor API; a clerk cannot de-tokenize or substitute an unrestricted token.
5. Reconcile the processor response, audit who initiated each transaction, retain only necessary receipt data and apply data-retention/deletion policies.

**Current-vs-target evidence:** T0 confirms the MedDefense billing MySQL files are unencrypted and billing application-to-MySQL transport does not enforce TLS; **no payment PAN storage or existing tokenization implementation has been demonstrated**. This is a proposed design, and PAN data flows must first be mapped with Billing, Sarah Park and the provider. See [`0-crypto_inventory.md`](0-crypto_inventory.md), §Financial/billing data and 1x02 Finding 006.

### 2.3 If the vault is compromised

- **Vault mapping and plaintext PAN exposed:** An attacker may correlate tokens with real card numbers and potentially misuse account data; initiate incident containment, revoke exposed payment credentials, isolate compromised systems, preserve logs and work with the processor/acquirer, DPO and response team on legal/PCI notification duties.
- **Encrypted vault stolen, independent keys remain secure:** Direct PAN recovery may be limited, but access paths, APIs, backups and key exposure must still be investigated; encryption does not prove there was no disclosure.
- **Only merchant tokens stolen:** PAN should not be reconstructable from random tokens alone, but attackers might abuse compromised processor API credentials to make unauthorized charges; revoke/rotate affected tokens and API credentials and investigate transactions.
- **Recovery:** Suspend unsafe de-tokenization, rotate compromised keys/credentials, reissue or re-tokenize mappings when indicated, rebuild from trusted backups, reconcile affected accounts and verify monitoring before resuming.

### 2.4 Tokenization versus simply encrypting PANs

| Dimension | Provider-based tokenization | MedDefense encrypts and stores PAN |
|---|---|---|
| Exposure on billing hosts | Only limited-purpose opaque tokens; PAN absent if the flow is correctly implemented. | Encrypted PAN remains stored and recoverable in MedDefense-controlled systems. |
| Key / vault management | Processor manages the high-risk vault and PAN keys; MedDefense still secures token/API permissions. | MedDefense must manage encryption/decryption, key custody, rotation, authorization and recovery. |
| Impact of theft | Tokens alone should not expose PAN, but payment API abuse remains possible. | Encrypted PAN may be exposed if keys or decryption permissions are compromised. |
| PCI DSS scope | **May be reduced**, subject to segmentation, data flows, token design and assessor determination; never automatically eliminated. | Systems storing and decrypting PAN typically remain in scope. |
| Disadvantages | Provider dependence, cost, outages, vendor lock-in, token portability limits and API authorization risk. | Greater control/portability for some workflows, but greater breach surface and security/operational burden. |

**Decision:** Use processor-hosted payment entry and provider tokenization by default; require the DPO/Billing owner, Security, Procurement and a qualified PCI assessor to validate scope, data processing agreements, vendor controls and transaction recovery. Tokenization is **not** encryption, does not alone provide compliance, and should not be sold as risk elimination. [PCI SSC tokenization guidance](https://www.pcisecuritystandards.org/documents/Tokenization_Guidelines_Info_Supplement.pdf); [PCI SSC scoping FAQ](https://www.pcisecuritystandards.org/faqs/1117/).

## 3. Data Masking by Job Role

**Scope:** Illustrative fictitious records and proposed **backend-enforced RBAC/ABAC**, not a confirmed MedDefense access-policy deployment. A clinician's authorized treatment access may legitimately include full clinical data; billing and reception generally need less. The source data must remain encrypted/protected and access logged; masking affects what each authorized role sees, not whether the backend stores sensitive data.

| Data Field | Full Value (privileged record) | Nurse — treating patient | Billing Clerk — authorized billing | Reception — check-in |
|---|---|---|---|---|
| **SSN** | `987-65-4321` | `XXX-XX-XXXX` | `XXX-XX-4321` **only if verified matching requires last four** | `XXX-XX-XXXX` |
| **Patient Name** | `Maria Gonzalez` | `Maria Gonzalez` | `Maria Gonzalez` | `Maria Gonzalez` (private check-in view only) |
| **Diagnosis** | `Type 2 Diabetes` | `Type 2 Diabetes` | `E11.9` **only when required for reimbursement; otherwise hidden** | `REDACTED` |

### Nine role/field justifications (one sentence per cell)

1. **SSN / Nurse:** Mask all SSN digits because treating a patient's diabetes does not normally require a national identifier in the clinical view.
2. **SSN / Billing:** Reveal only the last four digits for an explicitly approved identity or payer-match workflow; otherwise mask the whole identifier.
3. **SSN / Reception:** Mask the SSN completely because appointment check-in can use safer identity-verification fields.
4. **Name / Nurse:** Display the full patient name in an authorized clinical record to support positive identification and safe medication administration.
5. **Name / Billing:** Display the full name only for the assigned account so staff can reconcile invoices and payer claims accurately.
6. **Name / Reception:** Display the full name within an authenticated, non-public check-in screen to match the appointment to the correct patient.
7. **Diagnosis / Nurse:** Display the diagnosis to a treating nurse because it directly informs clinical assessment and safe care.
8. **Diagnosis / Billing:** Show the minimum necessary reimbursement code only when the claim requires it; note that `E11.9` still discloses diabetes and is sensitive health data.
9. **Diagnosis / Reception:** Redact the diagnosis because routine registration does not require knowledge of the patient's medical condition.

**Operational safeguards:** Apply field-level authorization at the server/API and in export/print paths; audit patient-record reads, claims exports and emergency break-glass exceptions; suppress SSN and diagnosis from general logs and notifications; deny bulk exports by default. The role policy requires clinical leadership/DPO review, especially for emergencies, legitimate treatment and payer requirements. The US SSN and HIPAA minimum-necessary framing are educational examples; MedDefense's Luxembourg operations must also follow applicable EU/Luxembourg privacy requirements. [HHS minimum-necessary guidance](https://www.hhs.gov/hipaa/for-professionals/privacy/guidance/minimum-necessary-requirement/index.html).

## 4. Steganography as a MedDefense DLP Threat Vector (Five Sentences)

Steganography threatens MedDefense because the hospital routinely exchanges large DICOM imaging files whose normal-looking contents could conceal additional information without appearing to be an ordinary document export. A malicious insider with access to patient records and an imaging workflow could attempt to hide confidential data in otherwise legitimate image-related content before sending it through an authorized transfer route. Compared with a straightforward CSV export or attachment, such misuse can evade simple filename, extension and keyword filters, while modification of image data might also compromise diagnostic integrity. The **proposed 1x03 C3 Wazuh SIEM** control would help by correlating PACS access, unusually large or unexpected exports, user identity, transfer destinations and abnormal activity, supported by **C1 network segmentation** and approved DICOM-aware DLP/content validation rather than relying on Wazuh alone. Biomedical/Radiology should validate approved destinations, DICOM metadata, integrity/provenance and image-handling rules with clinical safety review, since blanket image modification or automated blocking could interrupt patient care.

**Evidence boundaries:** 1x02 Finding 024 and T0 document **cleartext DICOM traffic** and unencrypted PACS image storage; they do **not** establish that steganographic exfiltration has occurred. The Wazuh monitoring (C3) and segmentation (C1) controls are **proposals** in [`../1x03_defense_blueprint/17-security_strategy.md`](../1x03_defense_blueprint/17-security_strategy.md), not proven deployed DLP tools. The [DICOM PS3.15 Security and System Management Profiles](https://dicom.nema.org/medical/Dicom/current/output/chtml/part15/PS3.15.html) provide relevant guidance on secure transport, signatures, auditing and attribute confidentiality; none automatically detects hidden payloads.
